# 레포지토리 하네스 구성

- 배포에 포함된 `references/rules/`가 기본 규칙이며, 별도 원본 저장소 없이 실행 가능. 작성자가 관리하는 원본은 저장소의 `docs/`
- 대상 프로젝트를 조사하고, 규칙을 해당 프로젝트에 맞게 반영한 뒤 검증까지 진행
- CLI나 다른 스킬 설치 없이 에이전트의 파일 읽기·쓰기와 사용 가능한 로컬 도구로 구성
- 구성 요청은 필수 Git·Webhook 연동 확인, 하네스 문서 구성, 실행 승인 방식과 GitHub 자동화 사용 여부 확인을 포함. 사용자가 설정 변경이나 자동화 구성을 선택하면 같은 작업에서 구성. 앱 제작, PR 생성, 시험 알림 전송을 준비 확인용으로 임의 실행하지 않음. 실제 구성·갱신에 필요한 Worktree와 작업 브랜치는 파일 수정 전에 준비
- Codex 최초 구성과 선택 기록이 없는 갱신은 아래 실행 승인 선택부터 시작. 질문을 보낸 상태와 사용자가 답변한 상태를 구분하며 답변 전에는 파일 수정과 명령별 승인 요청을 진행하지 않음

## 시작 시 실행 승인 선택

- 대상의 기존 지침과 `project.md`의 선택 기록, 현재 실행 환경을 권한 안에서 최소한으로 읽고 [Codex 실행 승인 설정](./references/rules/main.md#codex-실행-승인-설정)을 확인. 상세 프로젝트 분석·Worktree 생성·원격 인증 확인·설치보다 먼저 사용자 선택을 확인
- 최초 구성과 선택 기록이 없는 갱신에서는 `기존 설정 유지` / `승인 자동 검토` / `전체 권한` 중 방식을 첫 사용자 질문으로 제시. `전체 권한`은 명령별 샌드박스 승인 없이 실행하며 파일·네트워크 제한도 해제하는 선택임을 명확히 설명
- 사용 가능한 사용자 입력 수단으로 실제 질문하고 답변을 기다림. 도구가 없거나 응답을 받을 수 없으면 일반 메시지로 선택을 요청하고 선택 대기로 보고. 선택지 안내나 질문 도구 호출만으로 확인 완료로 처리하지 않음
- 설정 변경 시 `현재 프로젝트` / `사용자 전역`의 범위도 확인. 현재 프로젝트를 우선 제안하고 전역은 다른 프로젝트에도 영향을 준다는 설명 후 명시적으로 선택한 경우에만 적용. GitHub 자동화 선택은 별도 항목으로 함께 물을 수 있지만 승인 방식 질문을 뒤로 미루지 않음
- 이미 요청하거나 기록된 방식과 범위는 재확인하지 않음. 미응답·질문 중단·대기 시간 경과는 미확정이며 기본값으로 처리하지 않음. 방식과 필요한 범위가 확정되기 전에는 파일 수정·하네스 적용·완료 처리를 보류하고, 현재 권한 안의 독립적인 읽기 조사만 진행. 명령별 승인 요청을 반복하며 답변을 대신하지 않음
- 선택 후 [실행 승인 방식 확인과 적용](#실행-승인-방식-확인과-적용)을 진행. 기존 설정 유지는 현재 환경의 승인 절차로 이후 작업을 진행하고, 변경 선택은 설정 반영과 실제 적용 확인을 먼저 처리

질문 예시:

> 하네스 구성을 시작하기 전에 실행 승인 방식을 선택해 주세요. 기존 설정 유지 / 승인 자동 검토 / 전체 권한 중 어떤 방식을 사용할까요? 자동 검토는 샌드박스를 유지하고 승인 요청을 검토 에이전트가 처리하며 거절될 수 있습니다. 전체 권한은 명령별 샌드박스 승인 없이 실행하고 파일·네트워크 제한도 해제합니다. 변경한다면 현재 프로젝트와 사용자 전역 중 적용 범위도 선택해 주세요. 사용자 전역은 다른 프로젝트에도 영향을 줍니다.

## 원본과 대상 확인

- 스킬 경로는 이 `SKILL.md`가 있는 디렉터리. 심볼릭 링크로 등록되어 있으면 실제 파일 위치를 기준으로 확인
- 대상 경로는 사용자 지정 경로를 우선하고, 지정이 없으면 현재 작업 중인 프로젝트 사용
- [원본 경로와 갱신 기준](./references/update.md)을 읽고 기존 설치와 원본 경로를 확인
- 최초 구성은 이 스킬의 `references/rules/`를 사용. 사용자가 외부 원본을 지정했거나 이전에 외부 원본 사용을 기록한 경우에는 해당 경로를 사용
- 아래 링크는 포함된 규칙 기준. 외부 원본 모드에서는 동일한 파일명을 외부 경로에서 찾아 읽음
- 설치 대상이 원본 문서 폴더나 스킬 폴더 자체인 경우 덮어쓰지 않음. 대상 프로젝트 내부에 스킬이 설치된 일반적인 경우에는 설치된 스킬 파일을 보존하고 프로젝트 문서만 구성
- 포함된 규칙이 누락되거나 manifest 해시가 다르면 불완전한 설치로 보고 재설치를 안내. 외부 원본 경로 입력을 기본 요구사항으로 만들지 않음

## 참조 문서

- 항상 [워크플로우](./references/rules/main.md), [공통 규칙](./references/rules/code-base.md), [테스트](./references/rules/test.md), [브랜치 전략](./references/rules/git-branch.md)을 읽음
- 준비물 확인은 워크플로우의 `시작하기 전`을 적용하고, 작업 기록은 [문서작성](./references/rules/document-write.md) 규칙을 읽고 반영
- 프론트엔드가 있으면 [프론트엔드 규칙](./references/rules/code-base/front-end.md)과 [디자인 시스템](./references/rules/code-base/design-system.md)을 읽음
- 백엔드가 있으면 [백엔드 규칙](./references/rules/code-base/back-end.md)을 읽음
- 설치 결과 검증 시 [하네스 평가](./references/rules/evaluation.md)의 관련 시나리오 확인
- 알림 준비와 전송은 [Discord·Slack 알림](./references/rules/notifications.md), 기본 전송 도구는 [알림 스크립트](./scripts/notify.mjs) 참조
- 하네스 구성·갱신 시 [Codex 구독 자동화](./references/rules/codex-subscription.md)의 사용 여부 확인과 적용 조건을 함께 확인
- 대상에 기록할 정보는 [프로젝트 설정 양식](./assets/project.md)을 참고
- 실행 승인·자동화 선택은 각 절차에 따라 확인하고, 그 외 규칙은 충돌 없이 적용할 수 없는 부분만 사용자에게 확인. 기존 기술과 규칙을 우선한다는 원칙은 질문 없이 적용

## 작업 공간 준비

- 하네스 문서·설치 상태·스킬 설치 파일의 수정도 [브랜치 전략](./references/rules/git-branch.md)의 Worktree 필수 대상. 읽기 전용 분석 후 첫 파일 수정 전에 별도 Worktree와 작업 브랜치를 생성·확인
- 같은 작업의 후속 요청이면 확인된 Worktree를 재사용. 준비 실패 시 원래 작업 공간의 파일을 수정하지 않음
- 준비 후 대상 경로를 Worktree 루트로 전환하고 문서 구성·검증·커밋을 그 안에서 진행. 원래 작업 공간과 기존 사용자 변경은 보존
- 기존 `develop` 등 프로젝트 기준 브랜치와 override를 유지. Worktree 도입을 이유로 기준 브랜치나 기존 정책을 기본값으로 교체하지 않음

## 프로젝트 분석

- Codex를 사용하면 [시작 시 실행 승인 선택](#시작-시-실행-승인-선택)의 답변과 적용 상태를 먼저 확인. 미확정 상태에서는 명령별 승인이 필요한 분석을 진행하지 않음
- 기존 GitHub 자동화와 `project.md`의 사용자 선택을 확인. 선택 기록이 없으면 사용자가 별도로 요청하지 않아도 [구독 계정의 GitHub 자동화](#구독-계정의-github-자동화)에 따라 먼저 사용 여부를 질문
- Git CLI, 대상 저장소·원격·기준 브랜치, 원격 및 PR 인증, Discord 또는 Slack Webhook 연동을 구성·갱신 전 필수로 확인
- AI Agent와 Node.js/npm/npx 등 사용 도구의 상태도 확인. 필수 연동은 비적용이나 선택 항목으로 바꾸지 않음
- 스킬이 이미 실행 중이면 현재 사용 가능한 에이전트 정보를 활용. 설치된 스킬의 실행에 Python이나 원본 저장소를 요구하지 않음
- 필수 연동이 미준비 또는 미확인이면 부족한 항목과 필요한 조치를 모아서 안내하고 준비 대기로 보고. 조사와 기존 문서 확인은 가능하지만 새 하네스 문서와 상태 적용은 보류
- Webhook의 서비스, 전송 대상, 비밀정보 설정 이름, PR 알림을 실행할 명령·스크립트·자동화 또는 전송 도구를 확인. URL만 있거나 전송 경로가 없으면 미준비로 처리
- 기존 전송 도구가 없으면 포함된 `scripts/notify.mjs`를 사용. Node.js 20 이상과 환경변수 설정을 확인하고 스킬 내부 경로에서 `--dry-run` 실행. 대상·권한의 확인 근거가 갖춰지면 전송 경로 준비로 기록하고, 필수 연동 확인 후 대상 프로젝트로 복사
- 설정 근거와 실제 전송 검증 여부를 구분하고, 필수 연동 확인 후 `project.md`에 기록. 설정만 확인한 경우 실제 전송 성공으로 기록하지 않음
- 준비 상태 확인 중 인증정보와 Webhook URL을 출력하거나 저장하지 않으며, 외부 쓰기나 알림 전송으로 인증을 시험하지 않음
- 대상의 `AGENTS.md`, 하위 영역의 지침, README, 패키지와 워크스페이스 설정, CI, 테스트 설정, Git 상태를 확인
- 프론트엔드·백엔드·모노레포 여부, 언어와 도구, 패키지 매니저, 앱과 공통 패키지 경로를 파악
- 검증 명령은 실제 스크립트나 설정에서 확인하고 근거 경로를 기록. 관례만으로 명령을 생성하거나 통과를 추정하지 않음
- 모노레포는 앱과 패키지별 실행 위치 및 영향 관계를 구분
- 기준 브랜치는 기존 전략과 Git 정보로 확인. 확정할 수 없으면 필수 준비 미확인으로 기록하고 확인 요청
- Git 저장소가 아니면 필수 준비 미완료로 처리하고 저장소 준비 방법을 안내. `git init`이나 원격 생성을 임의로 실행하지 않음
- 비어 있는 프로젝트는 구조 미정으로 기록하고 기본 기술은 후보로만 제시. 앱이나 테스트 환경을 생성하지 않음
- 분석에 필요한 정보만 읽고 인증정보나 환경변수 값을 문서로 복사하지 않음

## 문서 구성

기존 하네스 문서 위치가 있으면 재사용하고, 없으면 `docs/harness/`를 사용한다. 아래는 기본 배치다.

```text
대상 프로젝트/
├── AGENTS.md
└── docs/harness/
    ├── project.md
    ├── main.md
    ├── code-base.md
    ├── code-base/
    │   ├── front-end.md
    │   ├── back-end.md
    │   └── design-system.md
    ├── test.md
    ├── git-branch.md
    ├── notifications.md
    ├── codex-subscription.md
    ├── document-write.md
    ├── evaluation.md
    ├── overrides/          # 프로젝트별 추가·대체·비적용 규칙이 있을 때 생성
    └── .harness-state/
        └── state.json      # 원본 경로와 해시만 기록
```

- 원본의 `main.md`, `code-base.md`, `code-base/`, `test.md`, `git-branch.md`, `document-write.md`, `notifications.md`, `codex-subscription.md`, `evaluation.md`를 위 구조에 공통 규칙으로 한 벌만 배치. 프로젝트별 조정은 override와 `project.md`에 기록. 자동화 안내 문서 배치와 실행 workflow 설치는 구분
- 기본 알림 도구를 선택하면 이 스킬의 `scripts/notify.mjs`를 대상 프로젝트의 `scripts/harness-notify.mjs`로 복사. 임시 스킬 경로에 의존하지 않도록 실제 프로젝트 경로의 명령을 `project.md`에 기록. 기존 전송 도구를 사용하면 복사하지 않음
- PR 알림은 [알림 본문 규격](./references/rules/notifications.md#pr-알림-전송)을 적용하고 기본 스크립트의 `--pr-file` 명령을 기록. 저장소·PR 제목·브랜치·주요 변경·검증별 상태·리뷰·남은 작업이 포함된 JSON 작성과 preview 확인을 절차에 연결. 기존 도구도 같은 정보를 포함하도록 연결
- 알림 본문은 섹션 사이 빈 줄, 항목별 줄바꿈, 검증 설명의 다음 줄 들여쓰기를 유지. 기존 도구를 연결할 때도 여러 줄을 한 문장으로 합치지 않고 preview와 전송 본문의 개행이 같은지 확인
- 기존 목적지 파일은 임의로 덮어쓰지 않으며, 갱신은 [갱신 기준](./references/update.md)의 스크립트 해시 확인 적용
- 링크 보존을 위해 규칙 문서 묶음을 함께 배치. 적용하지 않는 영역은 `project.md`와 override에 비적용 사유를 기록하고 공통 파일은 수정하지 않음
- `project.md`에 실제 기술, 영역별 경로와 검증 명령, 기준 브랜치, 문서 위치, 적용하지 않는 규칙, 미확정 항목을 기록
- 원본 모드(`bundled` 또는 `external`)와 경로를 `project.md`에 기록. 포함된 규칙은 manifest의 해시로 버전을 확인하며, 설치 대상 프로젝트의 Git 커밋을 스킬 버전으로 기록하지 않음. 상태 파일은 [갱신 기준](./references/update.md)에 따라 경로와 해시만 기록. `baseline/`과 `agents-block.md` 등 본문 사본은 생성하지 않음
- 공통 규칙의 신규 구성 기본값이 기존 기술과 다르면 override에 기존 기술과 대체할 항목을 명시. 설치만을 위해 기술을 변경하지 않음
- `project.md`에는 프로젝트의 실제 검증 명령과 실행 위치를 기록하고, 공통 테스트 규칙과 다른 항목은 `overrides/test.md`에 기록. 설정이 없는 검사는 미구축으로 구분
- `overrides/git-branch.md`에는 공통 규칙과 다른 기존 전략을 반영하고, `develop`이 없다고 새로 만들지 않음
- `project.md`에는 기존 작업 이력과 도메인 정책 문서 위치를 기록. 공통 작성 규격과 다른 부분은 `overrides/document-write.md`에 반영. 별도 위치가 없으면 `docs/history/`와 `docs/plan/`을 기본값으로 기록
- 실제 변경이 발생한 구성 작업은 문서작성 규격에 맞춰 기록. 기존 날짜 파일이 있으면 추가하고, 하네스 구성만으로 제품의 도메인 정책을 임의로 만들지 않음
- 변경 없는 재실행은 결과만 보고하고 작업 이력을 추가하거나 날짜를 바꾸지 않음
- 원본 `main.md`의 `Skills 활용`, `AGENTS.md`, `여러 프로젝트별 구축 필요`는 베이스 유지관리 항목이므로 대상의 운영 절차로 복사하지 않음. 대신 대상의 `project.md`, 루트 `AGENTS.md`, 설치된 `evaluation.md` 참조를 연결
- 문서가 다른 위치로 이동한 경우 모든 상대 링크를 새 위치 기준으로 수정

## 실행 승인 방식 확인과 적용

- [Codex 실행 승인 설정](./references/rules/main.md#codex-실행-승인-설정)을 읽고 현재 CLI 버전, 프로젝트·사용자 설정, 실행 옵션과 관리자 제약을 확인. 인증정보나 설정 원문 전체를 출력하지 않음
- [시작 시 실행 승인 선택](#시작-시-실행-승인-선택)에서 확정한 방식과 범위를 같은 작업에서 반영. 미응답 상태에서는 이 단계로 넘어가지 않음
- 첫 파일 수정 전 별도 Worktree와 작업 브랜치를 준비. 프로젝트 설정은 해당 Worktree의 `.codex/config.toml`, 명시적으로 선택한 전역 설정은 `~/.codex/config.toml`에 필요한 키만 반영. 파일 쓰기나 보호 경로 승인은 실행 환경의 절차 적용
- 기존 TOML의 내용과 주석을 보존하고 최상위 키 위치·중복·문법과 실제 diff를 확인. permission profile과 구형 sandbox 설정은 혼합하지 않고 기존 설정 체계와 CLI 옵션의 우선순위 확인. 지원하지 않거나 관리자 정책이 차단하면 제한을 유지하고 필요한 조치 보고
- `project.md`에 선택·근거·적용 범위·설정 경로·변경 키·파일 검증·실제 적용 확인 상태 기록. 재시작·프로젝트 신뢰·현재 세션의 `/permissions` 확인이 필요하면 미적용 또는 미확인으로 구분
- 변경 선택 후에는 설정 반영에 필요한 Worktree 준비와 보호 경로 승인만 환경 절차에 따라 진행. 실제 적용 전 명령별 승인이 필요한 후속 작업은 보류하고 재시작 또는 권한 전환과 실제 적용 확인 후 재개. 설정 파일을 바꾼 뒤 기존 세션에서 승인 요청을 계속 띄우지 않음
- 사용자별 설정과 선택 기록은 공통 규칙의 설치 해시로 관리하지 않음. 갱신 시 기존 선택과 사용자 변경을 보존하며 실제 설정 차이를 자동으로 되돌리지 않음. 다른 에이전트는 해당 도구의 기존 설정 적용

## 구독 계정의 GitHub 자동화

- 하네스 최초 구성 시 사용자가 별도로 요청하지 않아도 이슈 작성 → 구현·검증 → PR 생성과 PR 코멘트 후속 수정 흐름을 안내하고 함께 구성할지 질문. 비공개 GitHub 저장소와 전용 러너·구독 로그인 유지 조건을 함께 설명하고 `함께 구성` 또는 `구성하지 않음`으로 선택 확인
- 사용자가 이미 자동화 구성을 요청했거나 이전에 구성을 선택했다면 같은 질문을 반복하지 않고 바로 구성. 하네스 구성 중 답변한 경우에도 별도 구성 요청이나 재승인을 요구하지 않음
- 갱신 시 기존 자동화와 기록된 선택을 유지. 선택 기록이 없으면 사용 여부를 질문하고, 명시적으로 구성하지 않기로 한 프로젝트에는 반복 질문하지 않음. 사용자가 선택을 바꾸면 해당 요청 적용
- 답변 전에는 미확정으로 기록하고 자동화 적용을 보류. 답변을 기다리는 동안 독립적인 조사·검증은 진행 가능. 미응답을 구성하지 않음으로 처리하지 않음
- [구독 자동화](./references/rules/codex-subscription.md)를 읽고 비공개 GitHub 저장소, 전용 Linux self-hosted runner와 구독 로그인 유지, Git·PR·Webhook 및 검증 명령을 확인. 미준비 항목은 모아서 안내하고 실제 적용 완료로 보고하지 않음
- [Actions flow 필수 준비](./references/rules/codex-subscription.md#actions-flow-필수-준비)에 따라 자동화 전용 `auth.json`, 인증 Secret 갱신 방식의 GitHub 갱신용 토큰, 조직·저장소의 Actions PR 생성 허용, `main` 등 실제 기본 브랜치 반영을 각각 확인. 현재 템플릿의 영구 파일 유지와 별도 Secret 복원·갱신 구현 필요를 구분하고 파일 복사·Secret 등록만으로 실행 완료 처리하지 않음
- [workflow 템플릿](./assets/codex-subscription/workflow.yml)을 `.github/workflows/codex-subscription.yml`, [제어 스크립트](./assets/codex-subscription/automation.mjs)를 `.github/codex/automation.mjs`로 배치. 알림 도구는 기존 경로를 우선하고 없으면 기본 스크립트를 함께 복사
- 사용자 요청이 템플릿 제공만인 경우 준비 조건과 설정 양식을 제공하고 실제 러너·로그인·원격 설정은 완료로 처리하지 않음. 공개 저장소에는 이 인증 방식의 실행 워크플로우를 설치하지 않음
- 기존 파일은 보존. 기존 기준 브랜치·검증 명령·알림 경로에 맞게 조정하고, CI가 Worktree 준비와 커밋·PR을 처리하는 작업 권한은 프로젝트 override로 기록
- `project.md`에 사용자 선택(`함께 구성` / `구성하지 않음` / `미확정`)과 근거, 적용 여부, 원본과 배치 경로, 러너 라벨·인증 저장 위치, 설정 이름과 준비 상태, 검증 명령·실행 결과·미실행 항목 기록. 구성 선택과 준비 대기·실제 적용 완료는 구분. 토큰·로그인 파일·Webhook 원문은 기록하지 않음
- 배치한 workflow와 제어 스크립트의 실제 경로·SHA-256을 상태의 `installed_templates`에 기록하고 [갱신 기준](./references/update.md) 적용. 원격 기본 브랜치 반영과 실제 이벤트 실행 검증은 별도 상태로 보고

## AGENTS.md 연결과 재실행

- 프로젝트별 추가·대체·비적용 규칙은 기존 override 위치를 우선하고, 없으면 설치 문서 폴더의 `overrides/`에 기록. 공통 문서 전체를 복제하지 않고 달라지는 항목만 작성
- override에는 대상 문서와 항목, 적용 범위, 추가·대체·비적용 구분과 적용할 내용을 명시. `project.md`에 실제 파일 링크와 적용 범위를 기록하고, override가 없으면 없음으로 표시
- 사용자 요청과 기존 프로젝트 규칙을 우선하고, 그 범위 안에서 override를 공통 하네스 규칙보다 우선 적용. 대체·비적용된 공통 항목은 중복 적용하지 않으며 지정하지 않은 항목은 공통 규칙을 적용
- 구형 설치의 운영 문서에 포함된 프로젝트별 수정은 [전환 절차](./references/update.md#기존-기준-사본-구조-전환)에 따라 override로 보존한 뒤 공통 규칙과 분리

- 원본 저장소의 `AGENTS.md`는 복사하지 않음. 대상의 기존 내용을 보존하고 아래 경계로 구분한 하네스 참조 블록만 추가 또는 갱신
- 경계 블록이 여러 개이거나 닫히지 않았으면 자동 교체하지 않고 확인. 기존 본문과 하네스 규칙의 충돌은 기존 규칙을 우선하여 정리
- 재실행 시 같은 블록이나 파일을 중복 생성하지 않음. [갱신 기준](./references/update.md)에 따라 공통 규칙의 해시를 확인하고, 프로젝트 override를 보존하면서 원본 변경을 반영
- 설치 해시가 없거나 현재 문서와 다르면 사용자 변경을 확인하기 전 덮어쓰지 않음. 해석할 수 없는 충돌이 남아 있으면 문서와 상태를 갱신하지 않음
- 하위 `AGENTS.md`가 상위 규칙과 충돌하는 경우 해당 영역의 적용 범위를 `project.md`에 명시하고 하위 지침을 무조건 덮어쓰지 않음
- 상대 링크는 기본 경로가 아닌 실제 설치 위치 기준으로 작성

```markdown
<!-- repository-harness:start -->
## 레포지토리 하네스

- 작업 시작 시 [프로젝트 설정](./docs/harness/project.md)과 [워크플로우](./docs/harness/main.md)를 확인
- 프로젝트 설정에 연결된 현재 작업 범위의 override를 함께 읽고 공통 하네스 규칙보다 우선 적용. 대체·비적용된 공통 항목은 적용하지 않고, 지정하지 않은 항목은 공통 규칙을 적용
- 코드 변경은 [코드 베이스 규칙](./docs/harness/code-base.md), 검증은 [테스트](./docs/harness/test.md), 브랜치 작업은 [브랜치 전략](./docs/harness/git-branch.md)을 적용
- 작업 이력과 정책 문서는 [문서작성](./docs/harness/document-write.md) 규칙을 적용
- PR 알림은 [알림 규칙](./docs/harness/notifications.md)과 프로젝트 설정의 실제 전송 명령을 사용
- 사용자 요청과 기존 프로젝트 규칙을 우선하고, 현재 작업에 필요한 단계만 진행
<!-- repository-harness:end -->
```

## 검증과 완료

- Codex 최초 구성과 선택 기록 없는 갱신은 실행 승인 방식과 필요한 범위의 명시적 답변을 확인했는지 검사. 미응답이면 선택 대기이며 하네스 구성·갱신 완료로 처리하지 않음. 설정 변경은 파일 반영과 실제 적용 확인을 구분
- 공통 규칙이 한 벌만 존재하고 `.harness-state/`에 `state.json` 외의 본문 사본이 생성되지 않았는지 확인. 구형 설치 전환 시 남은 파일이 있으면 사유를 보고
- 생성하거나 수정한 문서의 상대 링크가 모두 실제 파일을 가리키는지 확인
- `project.md`에 적힌 명령과 경로가 실제 설정에 존재하는지 확인. 실행하지 않은 명령은 실행 검증 미실행으로 기록
- 준비 상태, 미준비 항목의 다음 조치, 작업 기록의 날짜·작성자·검증 결과가 실제 확인 내용과 일치하는지 확인
- 가능하면 `git diff --check`로 공백 오류를 확인하고, 작업 전 상태와 비교하여 기존 변경이 보존되었는지 검토
- Worktree 필수·같은 작업 재사용·준비 실패 시 수정 보류 시나리오를 갱신 평가에 포함. 문서 검토와 실제 실행 결과를 구분
- 재실행 시 기존 연결 블록과 사용자 수정이 보존되는지 확인. 실제 재실행하지 않았다면 실행 통과로 보고하지 않음
- 하네스 구성만으로 앱 전체 테스트·빌드·DB 마이그레이션을 실행하지 않음. 관련 코드 변경이나 별도 요청이 있을 때 설치된 테스트 규칙 적용
- 생성 파일, 적용한 기술과 규칙, 검증 결과, 미구축·미확정 항목을 보고
- Git 및 Webhook 필수 연동이 모두 준비되고 문서 연결과 구성 검증이 끝난 경우에만 하네스 구성 완료로 보고. 하나라도 미준비·미확인이면 준비 대기 상태와 남은 조치를 보고
- 앱 검증과 실제 알림 전송 검증은 수행 결과대로 별도 보고

## 사용 예시

```text
$repository-harness 이 프로젝트에 레포지토리 기반 하네스를 구성해줘.
$repository-harness /path/to/project에 기존 기술과 AGENTS.md를 유지하면서 구성해줘.
$repository-harness 기존 하네스를 현재 규칙으로 갱신하고 프로젝트별 수정은 유지해줘.
$repository-harness 규칙 원본은 /path/to/repository-harness이고, 대상은 /path/to/project야. 하네스를 구성해줘.
```

- 스킬 목록에 등록되지 않은 환경에서는 이 `SKILL.md`의 실제 경로를 에이전트에게 전달하여 읽고 실행하도록 요청 가능
- CLI로 설치한 후 기본 호출만으로 구성 가능. 규칙 원본 경로 지정은 외부 원본을 사용하려는 경우에만 필요
- 스킬을 업데이트한 뒤 하네스 갱신을 요청하면 프로젝트 override를 보존하며 공통 규칙을 갱신하고 구형 기준 사본 구조를 전환. 스킬 설치나 업데이트 자체가 대상 프로젝트의 하네스 구성을 실행하는 것은 아님
- 작성자는 `docs/` 변경 후 배포용 규칙을 생성하고, 구성 절차는 이 파일에서, 생성 문서 양식은 `assets/project.md`에서 관리
