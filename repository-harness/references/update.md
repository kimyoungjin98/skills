# 원본 경로와 갱신 기준

## 기존 설치 찾기

- Codex에서는 기존 지침과 `project.md`의 실행 승인 선택부터 최소한으로 확인. 기록이 없거나 미확정이면 [시작 시 실행 승인 선택](../SKILL.md#시작-시-실행-승인-선택)을 첫 사용자 질문으로 진행하고, 답변 전 명령별 승인이 필요한 준비 확인·파일 수정·상태 적용은 보류
- 구성·갱신 전에 [워크플로우](./rules/main.md)의 필수 Git·Webhook 연동 조건을 확인. 미준비·미확인이면 기존 파일과 상태를 보존하고 준비 대기로 보고
- 대상 `AGENTS.md`의 하네스 연결 블록에서 `project.md` 위치를 먼저 확인. 연결이 없으면 기본 위치인 `docs/harness/project.md` 확인
- 명시적인 외부 원본 지정이 있으면 `external` 모드로 사용. 사용자가 기본 포함 규칙 사용을 요청하면 `bundled` 모드로 전환
- 지정이 없고 기존 설정의 `source_mode`가 `external`이면 `project.md`의 경로와 상태 파일의 `source_dir`를 확인. 명시적으로 선택한 외부 원본이 없으면 다른 원본으로 바꾸지 말고 필요한 경로만 확인
- `source_mode`가 `bundled`이거나 최초 구성이면 현재 실행 중인 스킬의 `references/rules/` 사용. 이전 설치의 절대 경로가 남아 있어도 최신 스킬의 포함 규칙을 사용
- 구형 상태에 `source_mode`가 없고 원본 경로만 있으면 기존 외부 원본 선택을 유지. 기록된 경로가 현재 스킬의 포함 규칙 경로이면 `bundled`로 기록
- 저장소 루트를 지정한 경우 그 아래 `docs/`를 확인. 구형 배치는 루트에 `main.md` 등이 있으면 사용 가능
- 원본에 `main.md`, `code-base.md`, `test.md`, `git-branch.md`, `document-write.md`, `notifications.md`, `codex-subscription.md`, `evaluation.md`, `code-base/`가 모두 있는지 확인
- 포함 규칙 모드는 `manifest.json`의 `bundled_sha256`과 실제 문서 해시를 확인. 불일치하면 재설치가 필요하며 대상 문서는 보존
- 성공한 원본 경로는 실제 절대 경로로 `project.md`와 상태 파일에 기록. 경로를 찾았다는 사실만으로 설치 버전을 갱신하지 않음

## 제작 원본과 설치 버전

- 제작 저장소는 `docs/`와 `scripts/build_skill.py`, 배포 스킬은 `SKILL.md`와 `references/rules/`로 구분. 설치된 `.agents/skills/repository-harness/`만 있는 프로젝트에 제작 원본이 있다고 가정하지 않음
- 공통 규칙 자체를 수정하는 요청은 제작 저장소의 `docs/`에서 반영하고 `python3 scripts/build_skill.py`와 `python3 scripts/build_skill.py --check`로 배포 규칙·manifest를 생성·검증. `references/rules/`와 `manifest.json` 해시는 직접 편집하지 않음
- 다른 프로젝트의 해결 내용을 원본에 반영할 때는 기존 기준 브랜치·override·연결 블록을 공통 기본값으로 복사하지 않고 필요한 공통 규칙만 반영
- 제작 원본에 접근할 수 없으면 설치본만 수정하여 배포 완료로 보고하지 않음. 확인한 원본 위치와 남은 반영 작업을 보고
- 스킬 설치·갱신 시 `skills-lock.json`이 관리되는 프로젝트는 설치 도구가 실제 설치 버전에 맞게 갱신한 결과를 확인하고 함께 반영. 다른 스킬 항목을 보존하며 임의의 해시나 버전을 작성하지 않음
- 스킬 잠금 파일은 설치한 스킬 버전, `manifest.json`은 배포 규칙, `.harness-state/state.json`은 프로젝트에 적용한 파일을 확인하는 정보. 스킬만 갱신했다고 하네스 설치 해시를 바꾸지 않음

## 최초 구성 시 보존할 정보

- 공통 규칙은 설치 문서 폴더에 한 벌만 배치하고, 프로젝트별 차이는 `overrides/`와 `project.md`에 기록
- `.harness-state/`에는 `state.json`만 생성. `baseline/`, `agents-block.md`, 문서 본문을 담은 별도 사본은 생성하지 않음
- `state.json`에는 아래 정보를 기록
  - `schema_version`: `2`
  - `source_mode`: `bundled` 또는 `external`
  - `source_dir`: 확인한 규칙 원본 디렉터리. 포함 규칙 모드에서는 기록용이며 다음 실행은 현재 스킬 위치 기준
  - `source_files`: 사용한 원본 파일의 상대 경로와 SHA-256
  - `installed_files`: 실제 배치한 공통 규칙의 상대 경로와 SHA-256. 링크 조정 등 배치에 필요한 변경 이후의 해시
  - `installed_scripts`: 복사한 알림 스크립트의 프로젝트 루트 기준 상대 경로와 SHA-256. 기존 전송 도구를 사용하면 빈 객체. 구형 상태의 필드 누락은 관리 이력 없음으로 취급
  - `installed_templates`: 요청에 따라 배치한 GitHub 자동화 템플릿의 프로젝트 루트 기준 상대 경로와 SHA-256. 미선택은 빈 객체 또는 기존 필드 없음 유지. 사용자 조정 후 실제 설치 결과를 기록
  - `agents_block_sha256`: 생성한 하네스 연결 블록의 SHA-256
- `project.md`와 override는 프로젝트가 관리하는 문서이며 `installed_files`에 포함하지 않음
- 최초 구성 전 이미 존재하는 문서는 사용자 문서로 취급. 원본과 같다고 확인되지 않은 내용을 생성 결과로 등록하거나 덮어쓰지 않음

## 갱신

- Codex 실행 승인 방식과 적용 범위는 `project.md`의 선택과 실제 설정을 함께 확인. 선택 기록이 없거나 미확정이면 시작 단계에서 질문하고 명시적 답변까지 갱신 적용·완료 처리를 보류. 선택 후 같은 갱신 작업에서 반영하며 변경 방식의 실제 적용 전에는 명령별 승인이 필요한 후속 작업 보류. 기존 선택과 사용자 설정 변경은 보존하며 전역 변경은 해당 범위의 명시적 선택이 있을 때만 진행
- GitHub 자동화는 기존 구성과 `project.md`에 기록된 사용자 선택을 먼저 확인. 선택 기록이 없으면 사용자가 별도로 요청하지 않아도 함께 구성할지 질문하고, 선택하면 같은 갱신 작업에서 바로 구성. 명시적으로 구성하지 않기로 한 선택은 유지하고 반복 질문하지 않음. 답변 전에는 자동화 적용 보류
- GitHub 자동화 템플릿은 `installed_templates`와 현재 파일의 해시가 같은 경우에만 새 템플릿 적용. 수정·삭제되었거나 관리 이력이 없으면 사용자 변경으로 보존. 파일 갱신과 사용자가 새로 선택한 구성 작업을 구분하고, 선택 없이 자동화를 새로 설치하거나 원격 설정을 변경하지 않음
- 알림 스크립트는 `installed_scripts` 해시와 현재 파일이 같은 경우 새 포함 스크립트로 갱신. 해시가 다르거나 파일이 삭제되었으면 사용자 변경으로 보존. 관리 이력이 없는 기존 파일은 포함 스크립트와 동일한 경우에만 등록하고, 다르면 기존 도구로 유지하거나 필요한 판단을 확인
- PR 알림 형식 갱신은 스크립트의 `--pr-file` 지원, `project.md`의 실제 실행 명령과 자동화 템플릿의 호출을 함께 확인. 기존 도구를 유지하면 새 본문 항목을 연결하고, 사용자 수정으로 스크립트 갱신이 보류되면 새 옵션의 호출만 먼저 적용하지 않음
- `installed_files`의 해시와 현재 공통 규칙을 비교. 같으면 새 공통 규칙으로 교체 가능하며, 다르거나 파일이 삭제되었으면 사용자 변경으로 취급
- 해시는 변경 여부만 판별하며 이전 본문을 복원하지 못함. 직접 수정된 공통 규칙은 기존 원본을 확인할 수 있는 경우 차이를 override로 보존하고, 구분할 근거가 없으면 해당 파일을 보존한 채 필요한 판단만 확인
- override와 `project.md`를 새 원본으로 덮어쓰지 않음. 실제 프로젝트 설정이 변경된 항목만 근거에 따라 갱신. Worktree 정책·실제 경로·작업 브랜치·기준 커밋 항목은 추가하며 기존 기준 브랜치와 override 목록을 대체하지 않음
- 갱신 후보에 override를 우선 적용하여 검토. 명시적인 대체·비적용은 공통 규칙과 다르다는 이유만으로 충돌 처리하지 않음
- 원본 갱신으로 override 대상이 삭제되거나 의미가 바뀌어 적용 범위를 판단할 수 없으면 해당 부분만 확인하고, 임의로 override를 삭제하거나 공통 규칙으로 되돌리지 않음
- 원본에서 삭제된 공통 문서는 현재 파일이 기록된 해시와 같고 참조가 정리된 경우에만 삭제. 관리 목록에 없는 파일은 보존
- 연결 블록은 기록된 해시와 같으면 갱신. 다르면 기존 연결과 사용자 추가 내용을 보존하여 필요한 참조만 수정하고, 경계 손상이나 해석할 수 없는 충돌만 확인
- 원본과 프로젝트 설정이 바뀌지 않았다면 파일과 상태를 유지. 날짜나 표현만 바꾸기 위한 재생성은 하지 않음
- 상태가 없거나 손상되었으면 기존 파일을 사용자 문서로 보존하고, 확인 가능한 원본 및 변경 제안을 바탕으로 필요한 부분만 확인. 기준 사본을 새로 만들지 않음
- 후보와 복구용 임시 파일은 설치 문서 폴더 밖의 임시 위치에서 관리. 미해결 충돌이 있으면 설치 파일과 상태를 갱신하지 않음
- 링크, 명령 근거, override 적용과 사용자 변경 보존을 확인한 뒤 적용하고 상태 파일을 갱신. 쓰기 실패 시 이전 설치 상태로 복구하고 실패 지점을 보고
- `installed_files`는 설치 문서가 실제로 바뀐 항목만 적용 후 해시로 갱신. 변경 없는 문서의 해시와 기존 상태를 유지하고, 사용자 수정 파일의 해시를 새 설치 해시로 등록하여 덮어쓰기 허용 상태로 만들지 않음
- `source_files`, `installed_scripts`, `installed_templates`, `agents_block_sha256`은 각각 적용한 원본·스크립트·템플릿·연결 블록의 변경에 따라 갱신. override나 `project.md`만 변경된 경우 공통 문서의 설치 해시를 다시 쓰지 않음
- 갱신 완료 시 반영한 원본 변경, 유지한 프로젝트 규칙, 검증 결과를 구분하여 보고

## 기존 기준 사본 구조 전환

- `schema_version: 1` 또는 `baseline/`이 있는 설치는 갱신 시 위 구조로 전환. 기존 기준 사본은 전환을 위한 비교에만 사용하고 다시 생성하거나 갱신하지 않음
- 기존 상태의 해시로 기준 사본이 온전한지 확인한 뒤 이전 생성본과 현재 문서를 비교하여 사용자 수정·삭제를 식별
- 이전 생성본 자체에 포함된 프로젝트별 기술, 명령, 정책도 새 공통 규칙과 비교하여 `project.md`나 override로 보존. 현재 문서와 기준 사본의 차이만 옮기고 끝내지 않음
- 기존 override와 중복되거나 충돌하는 항목을 확인하고 적용 범위를 유지. 기준 사본이 없거나 손상되어 변경의 의도를 판단할 수 없으면 해당 파일과 상태를 보존하고 필요한 부분만 확인
- 기존 `project.md`와 연결 블록 밖의 AGENTS.md 내용은 보존. 경로가 바뀐 참조만 수정
- 전환 후보에서 프로젝트별 내용과 삭제 의도가 모두 유지되고 링크가 유효한지 확인한 뒤 공통 규칙 한 벌과 override를 적용하고 버전 2 상태로 전환
- 전환 검증이 완료되면 구형 상태에 등록된 기준 사본과 `agents-block.md`를 제거. 등록되지 않은 파일이나 수정된 기준 사본은 임의 삭제하지 않고 남은 항목과 사유를 보고하며, 빈 폴더만 정리
- 전환 실패 시 기존 문서와 상태를 복구. 기준 사본만 먼저 삭제하거나 전환 미완료를 완료로 보고하지 않음
