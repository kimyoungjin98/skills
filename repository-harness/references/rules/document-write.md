# 문서화

## 공통

- 대상 프로젝트의 기존 문서 위치와 작성 규격을 우선 적용
- 동작이나 정책 변경은 구현과 같은 PR에 반영. 하네스 구성만 요청된 경우 실제로 진행한 구성 내역을 기록하고 구현하지 않은 도메인 정책은 만들지 않음
- 원본 문서의 기존 내용과 이력을 보존하고 이번 변경에 해당하는 내용을 추가

## 문서 위치 결정과 이동

- 문서를 만들거나 옮기기 전에 `project.md`, 현재 작업에 해당하는 문서 작성 override, 기존 정책 문서와 README의 연결을 확인
- 사용자 요청이 문서 위치를 명시하면 해당 범위에서 우선 적용. 기존 규칙과 다르다는 이유만으로 재승인을 요청하지 않음
- 요청이 “README의 정책을 docs로 옮겨줘”처럼 상위 폴더만 지정한 경우, 세부 위치는 적용되는 프로젝트 규칙으로 결정. 별도 위치 규칙이 없는 새 도메인 정책은 `docs/plan/[도메인명].md`에 작성하며 `docs/` 바로 아래에 임의로 생성하지 않음
- 기존 정책을 README에 둔다는 규칙은 README에서 옮기라는 요청의 해당 범위에서 변경됨. 이를 모든 문서의 위치 규칙이나 다른 override를 바꾸라는 요청으로 확대하지 않음
- 같은 내용을 다루는 기존 기준 문서가 있으면 해당 문서에 반영하거나 링크로 연결. 문서 이름이 비슷하다는 이유로 내용을 생략하거나 관계없는 문서에 합치지 않음
- 이동 전 기존 위치·이동할 위치·적용 근거를 정리하고, 이동 후 내용 누락과 중복 여부 및 들어오고 나가는 상대 링크를 확인. 링크가 유효하다는 사실만으로 문서 위치 규칙까지 준수한 것으로 판단하지 않음
- README와 프로젝트 문서 안내는 실제 위치에 맞춰 갱신. override는 사용자 요청으로 변경된 위치를 반영하는 데 필요한 항목만 수정하고 근거를 기록. 잘못 선택한 위치를 정당화하려고 규칙을 바꾸지 않음
- 요청과 기존 규칙으로 판단할 수 있으면 질문 없이 진행. 여러 기준 문서가 충돌하여 어느 내용을 유지할지 결정할 수 없는 경우에만 필요한 사항을 모아서 확인

## 날짜 기반 작업 내역 기록

- 현재 날짜(YYYY-MM-DD)를 기준으로 작업한 내역을 기록한다.
- 기존 위치가 없으면 `docs/history/YYYY-MM-DD.md` 사용
- 작업 일시는 프로젝트에서 사용하는 시간대를 기준으로 기록하고, 지정이 없으면 작업 환경의 시간대를 함께 표시
- 규칙
  1. 파일명은 `YYYY-MM-DD.md`
  2. 날짜별로 한 파일 안에 작업 내역이 모두 기록된다.
  3. 규격
     - 제목
     - 작업 일시
     - 작업자(github)
     - 작업 내용
     - 구현 근거
     - 검증 결과와 남은 작업
- 작업자(github)는 확인된 계정을 기록. 확인할 수 없으면 미확인으로 표시하고 임의의 계정을 사용하지 않음
- 같은 날짜의 작업은 제목별로 추가하고 기존 작업 내용을 덮어쓰지 않음
- 날짜와 시간대는 파일 상단에 한 번 기록하고, 각 작업은 `HH:mm · 작업 제목` 형식의 2단계 제목으로 구분
- 작업자(github)는 제목 아래 한 줄로 기록. 작업마다 표와 소제목을 반복하지 않음
- 본문은 변경·이유·검증·남음의 짧은 목록으로 작성. 상세 내용이 길면 관련 문서를 링크하고, 중첩 목록은 피함
- 검증에는 결과와 확인 근거를 함께 적고, 실행하지 않은 검증을 통과로 표시하지 않음
- 남음에는 미실행 사유와 다음 확인을 기록하고, 작업 범위 제외 항목을 구분
- 기존 이력을 간결하게 정리할 때 작업 시각, 작성자, 변경 사실, 검증 결과와 미실행 상태를 보존
- 기본 작성 양식은 아래를 따르며, 대상 프로젝트에 기존 규격이 있으면 해당 규격을 우선 적용

```markdown
# YYYY-MM-DD 작업 내역

시간대: Asia/Seoul

## HH:mm · 작업 제목

작업자(github): 확인한 계정 또는 미확인

- **변경:** 변경한 내용
- **이유:** 변경이 필요한 이유
- **검증:** 결과와 실행 명령 또는 확인 근거
- **남음:** 미실행 항목과 다음 조치. 없으면 없음
```

## 도메인별 기획/정책 문서 기록

- **도메인(ex. 사용자, 결제, 예약... 등)**별로 기획 내용이나 정책을 기록하는 마크다운 문서 필요
- 규칙
  1. 파일 명은 `docs/plan/[도메인명].md`
  2. 어떠한 작업이 끝난 뒤 문서에 반영해야될 필요가 있다면 반영
  3. 변경 날짜, 변경 전후 내용, 변경 근거를 이력으로 기록
  4. 제안, 반영, 배포 상태를 구분하고 merge나 배포 전에 완료된 정책으로 기록하지 않음
