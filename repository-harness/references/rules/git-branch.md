# Git 브랜치 전략

- 기존 프로젝트에 브랜치 전략이 있을 경우 해당 전략을 우선 적용
- 아래 GitFlow는 별도 전략이 없는 신규 프로젝트의 기본값

## GitFlow

- `main` : 제품을 배포
- `develop` : 개발 브랜치, 해당 브랜치를 기준으로 작업한 기능들을 merge
- `feature` : 단위 기능을 개발하는 브랜치, 개발이 완료되면 develop에 merge
- `release` : 배포를 위해 main 브랜치로 보내기 전에 QA(품질검사)
- `hotfix` : main 브랜치로 배포를 했는데 버그가 생겼을 경우 긴급 수정

## Git Worktree

- 파일을 수정하는 작업은 규모와 종류에 관계없이 별도 Worktree와 작업 브랜치에서 진행. 문서·설정·단순 수정도 포함하며, 하네스 구성·갱신도 포함하며, 읽기 전용 조사·리뷰는 제외
- 수정 전 `git status --short`, `git branch --show-current`, `git worktree list`로 기존 변경과 현재 위치를 확인
- 별도 Worktree와 작업 브랜치를 생성한 뒤 그 경로에서만 파일 수정·의존성 설치·검증·커밋을 실행. 기존 작업 공간의 브랜치는 변경하지 않음
- 같은 작업을 이어가는 경우 해당 작업의 Worktree와 브랜치를 확인하여 재사용. 작업이 다르면 새로 생성하며, 기존 기능 브랜치에 있다는 이유만으로 생략하지 않음
- 사용자 지정 브랜치, 기존 프로젝트 기준 브랜치, `develop`, 원격 기본 브랜치 순서로 기준을 확인
- Worktree 도입 시 기존 프로젝트의 `develop` 등 기준 브랜치와 override를 유지하며, 공통 기본값으로 대체하지 않음
- 기준 브랜치를 확인할 수 없으면 임의로 생성하거나 추측하지 않고 사용자에게 확인
- 작업 브랜치는 `feature/<작업명>`, 경로는 쓰기 가능한 별도 작업 폴더를 사용하고 기존 경로와의 중복 확인
- 기존 브랜치가 다른 Worktree에서 사용 중이면 강제로 연결하지 않고 별도 작업 브랜치 생성
- 대상 브랜치의 최신 상태를 확인. 네트워크 문제로 확인하지 못하면 사용한 로컬 커밋과 사유 기록
- 생성 후 `git -C <작업 경로> rev-parse --show-toplevel`, `git -C <작업 경로> branch --show-current`, `git worktree list`로 별도 경로와 작업 브랜치를 확인하고 기준 커밋·브랜치·경로를 기록
- 위 확인이 끝나기 전에는 파일을 수정하지 않음. `main`, `develop`, `release` 등 공유 브랜치나 브랜치가 없는 상태(detached HEAD)에서 직접 작업하지 않음
- Worktree나 브랜치 생성에 실패하면 원인과 필요한 조치를 보고하고 수정은 보류. 원래 작업 공간에서 대신 수정하지 않음
- 사용자 요청이나 기존 프로젝트 규칙이 명시적으로 다른 방식을 지정하면 해당 지시와 근거를 기록. 작업이 단순하거나 번거롭다는 이유로 예외를 만들지 않음

## 서브모듈과 보존 작업 재개

- 서브모듈이 있으면 Worktree에서 초기화·인증·기준 커밋과 내부 변경을 확인. 내부 변경을 상위 저장소의 커밋으로 보존했다고 간주하지 않음
- 실패 작업을 재개하기 전 요청 식별자, 실제 Worktree·브랜치·기준 커밋, 로컬 변경·커밋과 원격 SHA를 확인. 상태가 다르면 덮어쓰거나 강제 push하지 않고 보존 후 필요한 부분만 확인
- push 이후 전달만 실패한 경우 보존된 커밋·검증 결과로 실패한 PR·댓글·알림 단계부터 복구. 복구를 위해 불필요하게 구현·검증을 다시 실행하지 않음
- 서브모듈이 초기화된 Worktree는 Git의 제거 제약과 내부 미커밋 변경을 확인하고 자동 강제 제거하지 않음. 조건이 충족되지 않으면 경로와 수동 정리 조치를 보고

## 정리와 실패 처리

- 사용자 변경사항을 보존하고 강제 checkout, reset, Worktree 삭제를 하지 않음
- 충돌 발생 시 충돌 파일과 원인을 확인하고, 사용자 의도가 필요한 부분만 확인 요청
- 작업이 실패하거나 PR 생성이 보류되면 Worktree와 변경사항을 보존하고 위치 및 남은 작업 보고
- Agent가 생성한 Worktree는 모든 변경이 커밋되고 원격에 push되어 있으며, 미추적 파일과 후속 로컬 검증이 없을 경우 정리 가능
- 기존 사용자 Worktree와 작업 브랜치는 임의로 삭제하지 않음
