# 레포지토리 기반 하네스 구축 계획

## 목표와 작업 권한

- 에이전트 워크플로우로 코딩을 자동화하고, 개발자는 업무 요청 후 PR을 검토하는 구조를 목표로 함
- 구현·수정 요청은 요청 범위의 조사, 계획, 파일 수정, 필요한 의존성 설치, 검증, 별도 Worktree와 작업 브랜치 생성, 커밋, 해당 원격 작업 브랜치로 push, PR 생성·갱신까지 포함. 각 단계의 진행 여부를 다시 묻지 않음
- 사용자 요청이나 프로젝트 규칙이 작업 범위를 제한하면 해당 제한을 우선 적용. 조사·리뷰만 요청한 경우 파일 수정이나 PR 생성을 임의로 진행하지 않음
- 이미 확인한 권한과 프로젝트 설정은 같은 범위의 후속 작업에도 적용. 에이전트가 문서·코드·설정으로 확인할 수 있는 내용은 직접 확인하며, 진행 상황 공유를 승인 대기로 바꾸지 않음
- 구현 방식과 검증 방법은 기존 규칙과 코드로 결정하고, 선택 근거는 PR에 기록. 답변 없이는 기대 동작을 정할 수 없는 정책, 요청 범위 밖의 작업, 기존 작업을 잃을 수 있는 조작만 필요한 내용을 모아서 확인
- merge, 배포, 운영 데이터 변경, 강제 push, 사용자 변경 삭제는 일반 구현 요청에 포함하지 않음
- PR 알림은 사용자가 전송을 요청했거나 프로젝트에 전송 대상과 자동 전송 권한이 정해져 있으면 해당 범위에서 실행. URL이나 인증정보가 있다는 사실만으로 전송 권한을 추정하지 않음
- 하네스의 작업 권한과 CLI 실행 환경의 권한은 구분. 환경이 요구하는 승인은 문서로 우회하지 않으며, 막힌 명령·사유·필요한 설정을 보고. 실행 승인 설정은 아래 선택 절차를 적용하고 사용자 전역 설정은 사용자가 해당 범위를 명시적으로 선택한 경우에만 변경

## 규칙 적용 순서

- 사용자 요청과 기존 프로젝트 규칙을 우선하고, 프로젝트 override는 공통 하네스 규칙보다 우선 적용
- 프로젝트 하네스가 구성된 경우 작업 시작 시 `project.md`에 기록된 override 목록과 적용 범위를 확인하고, 현재 작업에 해당하는 override를 공통 규칙과 함께 읽음
- override가 대체하거나 비적용으로 지정한 공통 규칙은 함께 적용하지 않음. 지정하지 않은 부분은 공통 규칙을 적용
- 공통 규칙과 다르다는 이유만으로 override를 무시하거나 선택을 다시 묻지 않음. override끼리 충돌하거나 대상과 적용 범위가 불명확하여 판단할 수 없는 부분만 확인
- 대상 프로젝트의 공통 하네스 문서는 한 벌만 유지하고 프로젝트별 차이는 override와 `project.md`에 기록. 갱신 상태는 경로와 해시만 보존하며 `baseline/` 등 문서 본문의 기준 사본은 생성하지 않음

## 시작하기 전

- Codex로 하네스를 최초 구성하거나 선택 기록 없이 갱신하는 경우 [실행 승인 설정](#codex-실행-승인-설정)을 첫 사용자 질문으로 확인. 기존 지침·선택 기록·실행 환경의 최소 읽기 확인 후, Worktree 생성·원격 인증 확인·설치 등 명령별 승인이 필요한 작업보다 먼저 질문하고 답변을 기다림
- Git CLI, 대상 저장소와 원격 인증, PR 생성 인증, Discord 또는 Slack Webhook 연동은 하네스 구성의 필수 조건
- 구성과 갱신 전에 필수 연동을 확인. 미준비 또는 미확인 항목이 있으면 필요한 조치를 모아서 안내하고 구성·갱신은 준비 대기로 보고
- 문서 구성만 요청된 경우에도 필수 연동을 생략하거나 비적용으로 바꾸지 않음. 조사와 기존 문서 확인은 진행할 수 있지만 필수 연동 확인 전 새 하네스 적용과 완료 처리는 보류
- 하네스 최초 구성 시 [Codex 구독 자동화](./codex-subscription.md#구성-시-사용-여부-확인)의 이슈·PR 코멘트 자동화를 함께 구성할지 질문. 사용자가 선택하면 같은 작업에서 바로 구성하고, 이미 정한 선택은 갱신에서도 유지. 선택 기록이 없는 갱신은 사용 여부를 확인

| 준비물 | 필요한 시점 | 확인 내용 |
| --- | --- | --- |
| AI Agent CLI (Codex, Claude Code... 등) | 하네스 구성과 작업 실행 | 에이전트 실행 및 필요한 계정 인증 완료 |
| Node.js와 npm/npx | Skills CLI 설치·갱신, 기본 알림 스크립트 실행(Node.js 20 이상) | `node --version`, `npm --version`, `npx --version` 실행 가능 |
| Git CLI | 구성·갱신 전 필수 | `git --version` 실행 가능, 대상 Git 저장소·원격·기준 브랜치 확인 |
| Git 원격 인증 | 구성·갱신 전 필수 | 해당 저장소에 필요한 읽기·쓰기 권한과 인증 상태 확인 |
| 호스팅 서비스 CLI 또는 API 인증 | 구성·갱신 전 필수 | 사용하는 서비스의 PR 생성 권한 확인. Git 원격 인증과 별도로 확인 |
| Discord 또는 Slack Webhook 연동 | 구성·갱신 전 필수 | 둘 중 사용할 서비스, 전송 대상, URL 설정, 전송 경로와 권한 확인 |
| Python 3 | 이 베이스의 기획 수정 후 배포용 규칙 생성 | `python3 --version` 실행 가능. 배포된 스킬 사용자에게는 불필요 |

- 설치와 원격 작업은 해당 서비스에 접근 가능한 네트워크 필요
- 인증정보와 Webhook URL 원문은 문서에 기록하지 않고 환경변수나 기존 비밀정보 저장소에서 관리. 문서에는 설정 이름과 준비 상태만 기록
- 준비 상태 확인을 위해 임의로 push, PR 생성, Webhook 테스트 전송을 실행하지 않음
- 설치·로그인·외부 연동이 필요한 경우 필요한 조치를 안내하고, 이미 준비된 항목은 다시 설정하지 않음
- Webhook은 URL 보유만으로 연동 완료로 판단하지 않음. PR 생성 이후 알림을 실행할 명령·스크립트·자동화 또는 사용 가능한 전송 도구와 설정 연결까지 확인
- 기존 전송 경로가 없으면 스킬에 포함된 기본 스크립트 사용. 준비와 실행 기준은 [Discord·Slack 알림](./notifications.md) 적용
- 설정 확인과 실제 전송 성공은 구분. 시험 전송 권한이 없으면 설정 확인 근거와 전송 검증 미실행을 기록

### Codex 실행 승인 설정

- 하네스 최초 구성과 선택 기록이 없는 갱신에서 아래 방식을 설명하고 사용자의 명시적인 답변을 필수로 확인. 기존 설정의 존재, 질문 도구 호출 성공, 답변 대기 시간 경과를 사용자 선택으로 처리하지 않음

| 선택 | 승인 정책 | 검토 주체 | 실행 권한 |
| --- | --- | --- | --- |
| 기존 설정 유지 | 현재 값 유지 | 현재 값 유지 | 현재 값 유지 |
| 승인 자동 검토 | `on-request` | `auto_review` | `workspace-write` |
| 전체 권한 | `never` | 승인 검토 없음 | `danger-full-access` |

- 자동 검토는 샌드박스를 유지하고 승인 요청을 별도 검토 에이전트가 처리하는 방식. 거절된 작업은 중단될 수 있음. 명령별 샌드박스 승인 없이 실행하려는 선택은 전체 권한이며 파일·네트워크 샌드박스 제한도 해제됨을 질문에 함께 설명. 특정 방식을 대신 선택하지 않음
- 설정 변경을 선택하면 적용 범위도 확인. 현재 프로젝트의 `.codex/config.toml`을 우선 제안하고, 사용자 전역 `~/.codex/config.toml`은 다른 프로젝트에도 영향을 준다는 설명과 해당 범위의 명시적 선택이 있을 때만 변경
- 이미 방식과 범위를 요청했거나 선택한 경우 같은 질문을 반복하지 않고 같은 구성 작업에서 반영. 미응답이나 범위 미확정 상태에서는 현재 권한 안의 독립적인 읽기 조사만 진행하고, 파일 수정·하네스 적용·완료 처리는 보류. 명령별 승인 요청을 이어가며 선택 확인을 대신하지 않으며 미응답을 기존 설정 유지나 전체 권한 동의로 처리하지 않음
- 기존 TOML의 모델·MCP·프로필·인증 관련 항목과 주석을 보존하고 선택에 필요한 최상위 키만 수정. `approval_policy`, `approvals_reviewer`, `sandbox_mode`를 적용하며, `never`만으로 샌드박스 제한까지 해제된다고 안내하지 않음
- permission profile을 사용하는 환경은 설치 버전과 기존 설정 체계를 유지. `default_permissions`의 `:workspace`·`:danger-full-access`와 구형 `sandbox_mode`·`sandbox_workspace_write`를 혼합하지 않으며, 상위 설정의 구형 키나 실행 옵션이 선택을 덮어쓰면 해당 근거와 필요한 조치 보고. 범위 밖 설정을 임의로 제거하지 않음
- 파일 수정 후 TOML 문법·중복 키·변경 범위를 확인하고 사용자 선택·근거·적용 경로·변경 키·검증 상태를 `project.md`에 기록. 사용자별 권한 설정은 공통 규칙의 `installed_files`에 포함하지 않음
- 프로젝트 설정은 신뢰한 프로젝트에서만 읽히며 CLI 옵션과 관리자 정책이 우선할 수 있음. 설정 파일 반영과 실제 실행 권한 적용을 구분하고 재시작 또는 `/permissions`에서의 확인이 필요한 상태를 기록. 현재 세션의 권한이 바로 바뀌었다고 보고하지 않음
- 승인 자동 검토·전체 권한을 선택한 뒤에는 설정 반영에 필요한 Worktree 준비와 보호 경로 승인만 환경 절차에 따라 진행. 선택한 방식이 현재 세션에 적용되기 전까지 명령별 승인이 필요한 후속 작업은 보류하고, 재시작이나 권한 전환과 실제 적용 확인 후 재개
- 설정 파일 자체가 보호되거나 관리자 정책이 선택을 막으면 환경의 승인 절차를 따르고 필요한 조치만 보고. 로그인 정보·토큰은 출력하지 않으며 관리자 요구사항을 낮추거나 실행 환경 제한을 우회하지 않음
- 갱신 시 선택한 방식과 범위를 유지. 실제 설정이 달라졌으면 사용자 변경을 보존하고 차이를 기록하며 자동으로 되돌리지 않음. 로컬 실행 설정과 GitHub 전용 러너의 실행 옵션은 적용 범위를 구분하여 기록
- 다른 에이전트를 사용하는 프로젝트는 해당 도구의 설정을 우선하며 Codex 전용 파일을 만들지 않음

공식 기준: [Codex 설정과 우선순위](https://learn.chatgpt.com/docs/config-file/config-basic), [샌드박스와 실행 승인](https://learn.chatgpt.com/docs/sandboxing), [승인 자동 검토](https://learn.chatgpt.com/docs/sandboxing/auto-review), [실행 권한 프로필](https://learn.chatgpt.com/docs/permissions).

## 작업·검증·전달 상태

- 구현, 검증, push, PR 생성·갱신, 대상별 댓글, 알림의 상태와 실패 사유를 각각 기록. 모델 검증과 자동화 재검증도 구분하고 하나의 성공으로 다른 단계의 성공을 추정하지 않음
- 최초 구성에서 변경 전달 정책을 확정하고 기존 프로젝트의 명시적인 정책과 승인 범위를 보존. `draft-on-incomplete`는 검증 통과 시 일반 PR, 실패·미실행·blocked 시 Draft PR로 전달. `verified-only`는 검증 통과 전 발행 보류. 이미 확정된 선택은 다시 묻지 않음
- 권한 위반, 보호 파일 변경, 브랜치·기준 커밋 무결성 문제는 정책과 관계없이 자동 발행 중단. 변경을 보존하고 사유와 필요한 조치를 보고
- 변경이 없으면 빈 PR을 시도하지 않고 기존 PR 또는 요청 이슈에 실제 결과와 검증 상태 기록
- 요청 이슈와 후속 요청이 발생한 PR에서 결과 PR 링크와 실제 검증 상태를 확인할 수 있게 전달. 기존 PR의 사용자 본문은 보존하고 명시된 관리 영역만 갱신. 경계 손상은 자동 덮어쓰기로 해결하지 않음
- 요청 식별자와 작업 브랜치·대상별 댓글 표식으로 중복 생성 방지. 일시적인 GitHub API 오류·응답 유실은 원격 상태 확인 후 정해진 횟수와 대기 시간 안에서만 재시도. 원격 조회 실패 시 쓰기 요청을 무조건 반복하지 않음
- push 이후 전달 실패는 보존된 커밋·검증 결과·전달 기록으로 실패 단계부터 복구. 브랜치·기준 커밋을 확인하고 구현·검증을 불필요하게 다시 실행하지 않음
- 댓글·알림·실패 보고의 오류는 최초 오류와 함께 별도 기록. 일부 댓글 또는 PR 전달 성공만으로 전체 완료 처리하거나 남은 복구를 건너뛰지 않음
- GitHub API의 원격 조회 기반 재시도와 Webhook의 수신 확인 기반 수동 재전송은 구분. Webhook 기준은 [알림 실패 처리](./notifications.md#전송-기준과-실패-처리) 적용
- Draft PR 발행은 결과 전달 상태이며 검증 통과나 완전한 작업 완료를 의미하지 않음. 구현·검증·전달 중 남은 단계와 다음 조치를 보고

## 프로세스

### 사용자 요청 (프롬프트)

- 사용자가 CLI 또는 프로젝트에 구성된 GitHub 자동화로 작업을 요청하는 단계
- 구독 계정의 이슈·PR 코멘트 자동화 구성은 사용자가 선택한 경우 [Codex 구독 자동화](./codex-subscription.md)의 적용 조건과 템플릿 사용
- 단순 작업일 경우 바로 진행
- 복잡하거나 단위가 큰 작업은 아래 항목을 중심으로 사용자 요청과 기존 문서·코드에서 구현의도를 파악
  1. DB 스키마 작성/수정/삭제
  2. 서비스 로직 작성/수정/변경
  3. 모듈 제작 및 구현
  4. (프론트의 경우) api -> response -> page 등의 데이터 fetch 아키텍처 구성
  5. 2 ~ 3 단계 뎁스가 들어가는 모듈이나 서비스 로직 구현
  6. 여러 페이지나 컴포넌트를 거치는 로직
- 작업 종류만으로 질문하지 않고 사용자 요청, 기존 코드, 문서로 결정할 수 있는 부분은 바로 진행
- 구현에 필요한 정책이나 동작을 결정할 수 없을 경우 사용자에게 필요한 질문을 모아서 확인
- 답변이 필요한 부분은 보류하고, 답변과 무관한 조사나 검증은 진행 가능
- 완료 조건 : 요청 범위, 기대 동작, 추가 확인이 필요한 부분이 구분되어 있음

### 구현 계획

- 사용자의 요청대로 구현 할 계획을 작성하는 단계
- 고려 해야할 사항
  1. 기대 동작과 변경 범위
  2. 기존 구조와 재사용할 코드
  3. DB, API, 공통 타입 등 다른 영역에 미치는 영향
  4. 요청한 작업을 기준으로 도출한 테스트 시나리오·기대 결과, 검증 명령과 통과 기준
  5. 변경에 따른 문서 반영과 실패 시 대응
- 단순 작업은 별도 계획 파일 없이 간단히 정리하고 진행
- 완료 조건 : 변경 대상과 검증 방법이 정해져 있고, 구현에 필요한 미확정 사항이 해소되어 있음

### 구현

- 사용자의 의도에 맞게 구현하는 단계
- 기능 구현·수정은 [테스트](./test.md)에 따라 테스트 코드 작성·수정을 포함. 사용자가 테스트 내용을 지정하지 않아도 요청한 작업과 기대 동작을 기준으로 작성
- 에이전트 위임은 사용자 요청이나 적용되는 프로젝트 규칙에 따라 사용
- 파일 수정 전에 [Git 브랜치 전략](./git-branch.md)에 따라 별도 Worktree와 작업 브랜치를 준비하고 경로·브랜치를 확인. 문서나 단순 수정도 생략하지 않으며, 준비 실패 시 원래 작업 공간에서 수정하지 않음
- 구현·검증·커밋은 확인된 Worktree에서 진행하고 원래 작업 공간은 보존. 작업 시작 전 기존 변경사항을 확인하고, 사용자 변경사항은 임의로 되돌리거나 커밋하지 않음
- 요청과 관련 없는 리팩터링이나 기술 변경은 포함하지 않음
- 완료 조건 : 계획한 동작과 관련 테스트 코드가 반영되어 있고, 변경 내역을 확인할 수 있음. 기존 테스트 재사용이나 작성 제외는 테스트 규칙에 따라 근거 기록

### 완료

#### Pull Request

- Git CLI로 변경사항을 관리하고, PR은 해당 호스팅 서비스의 CLI 또는 API 활용
- 변경이 있으면 위 작업·검증·전달 상태의 발행 정책에 따라 PR 생성·갱신. 권한과 무결성 위반은 자동 발행 중단
- 평가나 검토만 요청된 작업은 PR 생성 대상에서 제외
- 위 작업 권한과 프로젝트 설정에 따라 커밋·push·PR 생성을 연속 진행. 이미 허용된 작업에 별도 승인을 다시 요청하지 않음. 실행 환경이 승인을 요구하는 경우 diff, 검증 결과, PR 제목과 본문을 준비한 뒤 해당 명령의 승인 절차 적용
- 인증 실패 시 PR 생성만 중지하고, 완료한 작업과 검증 결과를 보존한 뒤 인증에 필요한 조치를 안내
- PR·댓글의 응답 유실과 일시적인 오류는 위 원격 상태 확인·중복 방지·제한 재시도 기준 적용
- 재시도 후에도 실패하면 원인, 현재 브랜치, 남은 작업을 보고
- 작성 요령
  1. 제목
  2. 작업한 내역 요약
  3. 리뷰할 때 중점적으로 검토해야 할 부분
  4. 구현 근거
  5. 체크 리스트
- 전달 조건 : PR 또는 변경 없는 결과의 링크와 실제 검증 상태를 보고. 구현·검증·push·PR·댓글·알림 상태를 분리하고 실패·대기·Draft 전달은 전체 작업 완료로 처리하지 않음
- PR 생성은 merge나 배포 권한을 포함하지 않음
- PR 생성·갱신 후 필수 연동으로 확인한 Discord 또는 Slack에 프로젝트에 정해진 전송 권한으로 알림 전송. [알림 본문 규격](./notifications.md#pr-알림-전송)에 따라 소유자/저장소·PR 제목과 링크·브랜치·주요 변경·검증별 결과·리뷰할 부분·남은 작업을 포함
- 전송 실패 시 PR 생성 성공과 알림 실패를 구분하고, 알림까지 완료된 것으로 보고하지 않음

#### 문서화

- [문서작성](./document-write.md)
- 동작이나 정책에 영향을 주는 문서는 구현과 같은 PR에 반영
- 문서 생성·이동 전에 [문서 위치 결정과 이동](./document-write.md#문서-위치-결정과-이동)에 따라 사용자 요청·문서 작성 override·기존 기준 문서를 확인. 잘못 선택한 위치에 맞춰 override를 변경하지 않음
- 날짜별 작업 이력과 도메인 정책 문서의 위치는 대상 프로젝트의 기존 구조를 우선
- 별도 구조가 없으면 작업 이력은 `docs/history/YYYY-MM-DD.md`, 도메인 정책은 `docs/plan/[도메인명].md` 사용
- 기록 항목과 정책 변경 이력은 문서작성 규칙을 적용하고, 같은 날짜의 작업은 기존 파일에 추가
- 이력에는 제안 또는 반영 상태를 구분하고, merge 전에는 배포된 정책으로 기록하지 않음
- merge 이후 기록 갱신이 필요한 프로젝트는 merge 이벤트로 실행되는 CI 등 별도 자동화로 처리
  - 실행 주체, 갱신할 문서, 중복 실행 방지 기준, 실패 확인 방법을 해당 프로젝트에 기록
  - 자동화가 없으면 후속 작업으로 보고하고 자동 갱신을 약속하지 않음
- 완료 조건 : 변경된 동작과 정책이 문서에 반영되어 있고, 후속 작업이 필요한 경우 담당 주체와 실행 조건이 기록되어 있음
