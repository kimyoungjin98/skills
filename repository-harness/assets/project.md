# 프로젝트 하네스 설정

## 적용 정보

- 구성 날짜 : 분석 결과로 작성
- 규칙 원본 모드 : `bundled`(스킬에 포함된 규칙) 또는 `external`(사용자 지정 원본)
- 규칙 원본 경로 : 확인한 원본 문서 디렉터리의 실제 절대 경로
- 하네스 원본과 버전 : 원본 위치와 커밋 또는 문서 해시
- 갱신 기준 : 설치 문서 폴더의 `.harness-state/state.json`의 설치 해시 사용. 공통 문서는 한 벌만 유지하고 기준 사본은 생성하지 않음
- 적용 범위 : 프론트엔드 / 백엔드 / 모노레포 / 구조 미정 중 해당 범위
- 규칙 우선순위 : 사용자 요청 → 기존 프로젝트 규칙 → 프로젝트 override → 공통 하네스 규칙. 베이스의 기술 지정은 신규 구성 기본값

## 프로젝트 override

- override 문서와 적용 범위 : 실제 파일 링크와 적용 범위를 기록. 없으면 없음
- 현재 작업에 해당하는 override를 공통 규칙과 함께 읽고 우선 적용
- 대체·비적용된 공통 항목은 함께 적용하지 않고, 지정하지 않은 부분은 공통 규칙을 적용

## 준비 상태

| 준비물 | 필요한 시점 | 확인 상태 | 다음 조치 |
| --- | --- | --- | --- |
| AI Agent CLI와 계정 | 구성 및 작업 실행 | 준비 / 미준비 / 미확인 | 확인 결과로 작성 |
| Node.js와 npm/npx | Skills CLI 설치·갱신, 기본 알림 실행(Node.js 20 이상) | 준비 / 미준비 / 미확인 | 확인 결과로 작성 |
| Git CLI·저장소·원격 인증 | 구성·갱신 전 필수 | 준비 / 미준비 / 미확인 | 기준 브랜치, 로컬 도구와 원격 인증을 구분 |
| 호스팅 서비스 CLI/API 인증 | 구성·갱신 전 필수 | 준비 / 미준비 / 미확인 | PR 생성 권한 확인 결과 |
| Discord 또는 Slack Webhook | 구성·갱신 전 필수 | 준비 / 미준비 / 미확인 | 서비스·전송 대상·설정 이름·전송 경로·권한 기록 |

- 준비 상태는 확인 가능한 정보로 기록하고, 확인하지 못한 인증이나 연동은 미확인으로 표시
- 필수 연동은 비적용으로 기록하지 않음. 모두 준비되기 전에는 하네스 구성·갱신을 완료로 표시하지 않음
- Webhook 설정 확인 근거와 실제 전송 검증 결과를 구분. 시험 전송하지 않았으면 전송 검증 미실행으로 기록
- 인증정보와 Webhook URL 원문은 기록하지 않음
- Python 3는 베이스의 배포용 규칙 생성에만 필요하므로 대상 프로젝트의 필수 준비물로 추가하지 않음

## 검증 명령

| 영역 | 검사 | 실행 위치 | 명령 | 설정 근거 | 구성 시 실행 결과 |
| --- | --- | --- | --- | --- | --- |
| 분석한 영역으로 작성 | lint / 타입 / 테스트 / 빌드 등 | 실제 경로 | 실제 명령 또는 미구축 | 근거 경로 | 통과 / 실패 / 미실행 및 사유 |

- 해당하지 않는 검사는 비적용 사유를 기록
- 명령이 확인되었다는 사실과 실제 실행 통과를 구분
- DB 검증은 격리된 환경에서 진행하고 접속정보는 이 문서에 기록하지 않음

## 브랜치와 PR

- 작업 권한 : 구현 요청은 조사·구현·검증·작업 브랜치 생성·커밋·push·PR 생성·갱신까지 포함. 이미 허용된 단계는 다시 묻지 않으며, 사용자 요청과 기존 프로젝트 규칙의 제한을 우선 적용
- 프로젝트별 제한과 근거 : 확인된 제한 또는 없음. 사용자에게 매번 재승인을 받는 항목으로 사용하지 않음
- CLI 실행 권한 : 작업 경로 쓰기·검증 명령·원격 접근의 확인 결과와 제한 기록. 하네스의 작업 권한과 환경의 승인 요구를 구분
- 작업 공간 : 파일 수정 전 별도 Worktree와 작업 브랜치 필수. 같은 작업의 후속 요청은 해당 공간을 재사용하고, 생성·확인 실패 시 수정 보류
- Worktree 경로와 작업 브랜치 : 작업 시 실제 경로·브랜치·기준 커밋 기록. 원래 작업 공간의 브랜치는 유지
- 갱신 시 보존 : 작업 공간 항목은 기존 설정에 추가. 프로젝트 기준 브랜치·PR 대상·override 목록과 적용 범위는 유지
- 브랜치 전략과 확인 근거 : 분석 결과로 작성
- 기준 브랜치 : 실제 브랜치 또는 미확정
- PR 대상과 사용 도구 : 확인된 설정 또는 미구축
- merge 및 배포 : PR 생성과 별도 권한으로 처리

## Codex 실행 승인 설정

- 사용자 선택과 근거 : `기존 설정 유지` / `승인 자동 검토` / `전체 권한` / `미확정`. 기존 선택과 요청 근거 기록. 다른 에이전트는 해당 도구와 비적용 사유 기록
- 시작 시 확인 상태 : 첫 질문의 방식·효과 안내와 명시적 답변 근거 기록. 미응답은 선택 대기이며 파일 수정·하네스 적용·완료 처리 보류. 질문 도구 호출이나 대기 시간 경과를 답변으로 처리하지 않음
- 적용 범위와 경로 : 현재 프로젝트의 `.codex/config.toml` 또는 명시적으로 선택한 사용자 전역 설정의 실제 경로. 전역 선택은 다른 프로젝트에 미치는 영향과 선택 근거 기록
- 현재 설정과 변경 : CLI 버전, 승인 정책·검토 주체·sandbox 또는 permission profile, 변경한 키와 기존 설정 보존 결과. 인증정보는 기록하지 않음
- 파일 검증과 실제 적용 : TOML 문법·중복 키·diff 확인 결과, 프로젝트 신뢰·재시작·현재 세션 확인 및 CLI 옵션·관리자 제약. 파일 반영과 실제 실행 권한 적용을 구분
- 후속 작업 재개 조건 : 설정 변경 시 실제 적용 확인 전 명령별 승인이 필요한 작업 보류. 설정 반영에 필요한 Worktree·보호 경로 승인은 환경 절차를 따르고 실제 적용 근거 확인 후 재개
- 갱신 시 보존 : 선택한 방식·범위와 사용자 수정 유지. 실제 설정과 기록의 차이는 확인 근거와 함께 기록하고 자동으로 되돌리지 않음

## GitHub 구독 자동화

- 사용자 선택과 근거 : `함께 구성` / `구성하지 않음` / `미확정`. 최초 구성과 선택 기록이 없는 갱신에서 확인한 답변·요청 근거 기록. 이미 정한 선택은 유지
- PR 발행 정책 : `draft-on-incomplete` / `verified-only` 또는 기존 명시적 정책. 최초 확정 근거와 override 기록. 기존 정책 보존
- 작업·검증·전달 기록 : 구현·모델 검증·자동화 재검증·push·PR·대상별 댓글·알림 상태, 요청 식별자, 최초 오류, 보존 기록 경로. Draft 전달은 검증 통과·작업 완료와 구분
- 복구 설정 : 영구 상태·Worktree 경로, 보호 파일, 원격 조회·재시도 제한, Webhook 수신 확인과 수동 복구 담당·절차
- 실행 사전 점검 : 실제 서비스 계정·작업 위치·PATH·CLI 버전·인증 경로·방식·샌드박스·프로젝트 도구의 확인 근거와 미실행 항목
- 프로젝트 검증 환경 : 테스트 전용 설정·쓰기 가능한 캐시와 산출물 경로·준비 명령·서브모듈 처리. 운영 비밀정보 값 기록 금지
- GitHub 권한 : 저장소 접근·push, workflow push, 조직 조회, 조직·저장소 Actions PR 생성 정책 각각 기록
- 러너 접근 : 기존 Linux 러너 재사용·조직 재등록 여부, 그룹·허용 저장소·라벨·온라인 상태, 서비스 관리 계정과 실행 계정 차이
- 활성화 단계 : 파일 배치 / 외부 준비 / 기본 브랜치 반영 / 실제 이벤트 / PR·댓글 전달 / 알림 수신 각각 기록. 기본 브랜치의 배포 연결과 승인 범위 확인
- 적용 여부 : 함께 구성을 선택하면 같은 작업에서 바로 구성. 사용자 선택과 준비 대기·실제 적용 완료를 구분하며, 답변 전에는 자동화 적용 보류
- 적용 조건과 준비 상태 : 비공개 저장소·전용 Linux 러너·구독 로그인 유지·Git·PR·Webhook·검증 명령의 준비 결과
- 템플릿과 배치 경로 : 적용한 원본과 실제 workflow·제어 스크립트 위치. 상태의 `installed_templates`로 변경 추적
- 러너와 인증 : 전용 러너 한 개의 라벨과 서비스 계정·영구 인증 경로. 로그인 파일 원문 기록 금지
- 인증 등록·갱신 : 자동화 전용 `auth.json`의 준비 상태와 영구 파일 유지 / 인증 Secret 복원·갱신 중 실제 방식 기록. Secret 방식이면 이름·복원 및 저장 단계·구현 여부·다음 실행 검증 결과 기록. 원문 기록 금지
- GitHub 갱신용 토큰 : 인증 Secret 갱신 방식이면 Secret 이름·대상·권한·만료·연결 단계와 준비 상태 기록. push·PR용 인증과 구분하며 영구 파일 방식이면 불필요 근거 기록
- Actions PR 생성 허용 : 조직·저장소 설정의 확인 근거와 관리자 조치, workflow의 contents·issues·pull-requests 권한을 구분하여 기록
- 기본 브랜치 반영 : `main` 등 실제 기본 브랜치·workflow와 제어 파일 경로·반영 커밋·반영 대기 또는 확인 결과 기록. 구현 작업의 기준 브랜치와 구분
- 작업 설정 : 기존 기준 브랜치·실제 검증 명령·알림 경로·Variables와 Secrets 이름. CI의 Worktree 준비·커밋·PR 권한 override 연결
- 적용·검증 상태 : 파일 준비, 기본 브랜치 반영, 실제 이슈·PR 코멘트 실행과 알림 검증을 구분. 미실행 항목과 필요한 운영 조치 기록

## 문서와 후속 작업

- 작업 이력 위치 : 기존 경로 우선, 없으면 `docs/history/YYYY-MM-DD.md`
- 도메인 정책 위치 : 기존 경로 우선, 없으면 `docs/plan/[도메인명].md` (관련 정책 변경 시 작성)
- 문서 작성 규격 : 설치된 `document-write.md` 참조
- merge 이후 자동화 : 기존 실행 주체와 조건 또는 미구축
- 알림 연동 : 필수. 사용할 서비스, 대상, 비밀정보 설정 이름, PR 알림 전송 경로와 권한 기록. 인증정보는 기록하지 않음

- 알림 실행 명령 : 기존 도구 또는 `node scripts/harness-notify.mjs --provider discord --pr-file <PR 알림 JSON 파일>`처럼 실제 경로와 선택한 서비스 기록
- 알림 본문 : 소유자/저장소·PR 제목과 링크·생성/갱신·브랜치·주요 변경·검증별 상태와 근거·리뷰할 부분·남은 작업 포함. 실제 PR 메타데이터와 실행 결과로 작성하고 preview 확인 경로 기록
- 알림 전송 권한 : 사용자 요청 또는 기존 프로젝트 규칙의 근거와 허용 대상·시점 기록. PR 자동 알림이 허용되면 매번 재확인하지 않음. URL 보유만으로 권한을 추정하지 않음
- 알림 검증 : 설정 확인 근거와 `--dry-run` 결과, 실제 전송 검증 결과 또는 미실행 사유 구분

## 예외와 미확정 항목

- 기존 규칙을 유지하여 적용하지 않은 기본값과 사유를 기록
- 비적용 영역과 사유를 기록
- 확인이 필요한 항목은 확인 시점과 함께 기록. 없는 경우 없음으로 작성
